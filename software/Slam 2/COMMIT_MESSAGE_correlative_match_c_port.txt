feat(slam_core): port correlative_match to C, validate on real Milk-V Duo S hardware

Ports correlative_match.py (coarse pose search) to C, builds a 3-level
testing bridge to validate it against the existing Python stack without
editing any existing files, finds and fixes 3 real bugs along the way
(one in the port's build, two in the benchmarking methodology itself),
and validates on real Duo S hardware rather than trusting host/QEMU
numbers. Net result: ~15x faster than the Python it replaces on real
hardware, confirmed by measurement -- but still ~1.9-2x over the
100ms/10Hz budget at realistic map sizes. NOT a complete fix. Follow-up
(lookup table for the Gaussian falloff) is designed but not implemented
-- see "Not done" section below.


WHY
---
correlative_match.py was measured at 2465-3298ms/call on the real Duo S
at n_static=60 (slam_progress_compact.md) -- 25-33x over budget, already
confirmed to be CPython/numpy interpreter overhead, not a BLAS/math
problem. This commit is the C port that overhead requires, plus the
infrastructure to actually trust it rather than assume it.

PORT DESIGN
-----------
Direct translation of correlative_match.py's SCALAR reference path
(_score_candidate / _coarse_sweep_topk / _greedy_refine -- the
pre-numpy-vectorization shape, per that module's own docstring, since
numpy has no C equivalent). Both layers preserved: Layer 1 coarse
top-K-distinct sweep, Layer 2 independent greedy local refinement per
candidate. All tunable constants carried over unchanged in value
(CORR_ prefix, e.g. CORR_MAX_STATIC_ENTRIES_SEARCHED=70).

- ScanFeature = typedef alias for messages.h's Feature struct (wire
  protocol struct already carries every field a scan feature dict did).
- CorrMapEntry = minimal stand-in for the real MapEntry (map_manager.c
  doesn't exist yet). Fields (angle, distance, mx, my, status, active)
  deliberately named to match map_manager.py's MapEntry exactly, so
  this becomes a pure rename once map_manager.h exists.
- No malloc anywhere, every array fixed-size/stack-allocated. float
  throughout, no double. Compiles clean (-Wall -Wextra -Wsign-compare,
  zero warnings) with host gcc AND
  aarch64-linux-gnu-gcc -O2 -ffast-math -march=armv8-a (exact flags
  slam_build_prompt.md specifies).
- CoarseResult struct mirrors the Python CoarseResult namedtuple
  exactly (dx, dy, dtheta, score, n_static, valid, ambiguous, second_score).


TESTING INFRASTRUCTURE (3 levels of trust, built because the rest of
slam_core is still pure Python and a bridge was needed to exercise the
C code through the real stack, not just in isolation)
---------------------------------------------------------------------
1. Standalone C self-test (test_correlative_match.c) -- mirrors
   correlative_match.py's T1-T7 (T8/T9 don't apply, those only exist to
   cross-check Python's numpy path against its own scalar reference;
   this port has one scoring path). PASSED on real Duo S hardware, not
   just QEMU.

2. Numeric parity vs Python reference (crosscheck_parity.py) -- feeds
   IDENTICAL inputs to correlative_match.py (double precision) and the
   ctypes-wrapped C code (single precision), diffs outputs with a loose
   float32-vs-float64 tolerance. Covers nominal recovery, too-few-
   anchors, parallel-wall ambiguity, arc-resolves-ambiguity, layer-2
   reach. ALL PASSED, exact agreement.

3. Swapped into the real, unmodified slam.py
   (run_slam_selftest_with_c_backend.py) -- sys.modules swap before
   slam.py's own import fires. ALL 12 of slam.py's own self-tests
   passed (stationary tracking, injected motion, parallel-wall slide,
   combined rotate+translate, ambiguity gating, confidence-gain jitter
   damping).

Same sys.modules trick reused by run_lidar_visualizer_with_c_backend.py
(real-LiDAR ROS2 path) and bench_with_c_backend.py
(bench_full_pipeline.py).


BUGS FOUND AND FIXED (in the order found)
------------------------------------------

Bug 1 -- ctypes marshalling cost contaminated the first speed comparison
  Symptom: full pipeline through the ctypes bridge only showed ~1.3-1.5x
    speedup over Python on host -- looked like the C port barely helped.
  Root cause: the ctypes wrapper still does real per-scan Python work
    (building ctypes.Structure objects from dicts/objects) before ever
    reaching C; that cost was contaminating the "C vs Python" comparison.
  Fix: isolated pure algorithm cost by pre-building ctypes buffers
    OUTSIDE the timing loop. Led directly to profiling the real Python
    search() with cProfile instead of guessing -- see PROFILING below.

Bug 2 -- benchmark's own RNG seeding produced non-monotonic,
  untrustworthy on-device results
  Symptom (real Duo S, bench_correlative_standalone_arm64 v1):
    n_static=10 -> 17.156ms
    n_static=60 -> 217.393ms
    n_static=200 -> 123.667ms   <- LESS than n_static=60, impossible
    n_static=400 -> 331.732ms
  Root cause: srand(42) called once at the top, map generation AND scan
    generation both drew from the same continuing rand() stream.
    Different n_static values consumed different amounts of the stream
    before scan generation began, so different n_static values were
    silently testing DIFFERENT SCAN DATA too, not just different map
    sizes -- not a fair comparison.
  Fix (bench_correlative_standalone_v2.c): independent fixed seeds --
    srand(42) for map, srand(777) for scan -- so scan is byte-identical
    across every map size tested. Added real statistics (mean, median,
    min, max, p95, stddev across ALL individual calls, not one averaged
    number) plus best-effort cpufreq governor/thermal read, specifically
    to answer the "is this scheduling jitter" question with data instead
    of guessing.
  Result after fix: clean, low-variance, trustworthy data -- see BENCH
    RESULTS below.

Bug 3 -- libcorrelative_match_arm64.so failed to load on the board
  Symptom:
    OSError: /lib/libm.so.6: version `GLIBC_2.35' not found (required
    by /root/Slam 2/libcorrelative_match_arm64.so)
  Root cause: the Ubuntu-hosted aarch64-linux-gnu-gcc cross-toolchain
    links against a newer glibc than the Duo S's Buildroot glibc has.
    Confirmed via `objdump -T`: original .so required symbol versions
    up to GLIBC_2.38. The static binaries (test_correlative_match_arm64,
    bench_correlative_standalone_v2_arm64) never hit this because static
    linking bundles its own libc/libm -- bug specific to the ONE
    dynamically-linked artifact (the .so the ctypes bridge needs).
  Fix: rebuilt with libm statically embedded instead of dynamically
    linked (-Wl,-Bstatic -lm -Wl,-Bdynamic). Confirmed via objdump -T
    the requirement dropped to just GLIBC_2.17 (2012-era, essentially
    guaranteed present) + GLIBC_PRIVATE (internal linker marker, not a
    real runtime constraint).
  Verified NOT just by inspecting symbols: wrote a dlopen/dlsym C
    harness calling correlative_search() through the rebuilt .so
    exactly the way ctypes would, ran it under qemu-aarch64-static,
    confirmed a real call succeeds (output: "dlopen'd .so call
    succeeded: valid=1 n_static=3 score=1.000").
  Confirmed fixed on real hardware: bench_with_c_backend.py ran
    successfully on the Duo S after this fix.


PROFILING -- WHAT WAS ACTUALLY SLOW, AND THE TWO FIXES APPLIED
----------------------------------------------------------------
Profiled the real Python search() directly with cProfile (n_static=60,
27 scan features, no ctypes/slam.py involved -- pure apples-to-apples),
rather than assuming "C is faster than Python" would be enough.

  Component                                              ms/call   % total
  ------------------------------------------------------ -------   -------
  Python for-loop + numpy CALL overhead (per scan          80.37    81.6%
    feature, ~2,241 iterations/call, each paying numpy's
    fixed per-op dispatch/allocation cost on grids of
    just 25-81 cells -- _score_grid_vectorized only
    vectorizes across the dx,dy grid, NOT across scan
    features)
  Other Python orchestration (_greedy_refine,                9.63     ~9%
    _coarse_sweep_topk, _prerotate_features,
    _insert_topk_distinct)
  Actual numpy math (vectorized exp/broadcast/max ops        8.50     ~9%
    genuinely computing something)
  TOTAL                                                     98.50    100%

Finding: only ~9% of Python's time was floating-point work. The other
91% was interpreter + numpy per-call dispatch overhead.

First isolated pure-C algorithm cost (ctypes buffers pre-built OUTSIDE
the timing loop, no marshalling): 33.0 ms/call, BEFORE any C-side
optimization -- notably SLOWER than Python's own actual math (8.5ms),
because the naive C loop called expf() once at a time (scalar libm)
while numpy's vectorized ufuncs use SIMD internally. Confirms: being C
doesn't automatically make raw transcendental throughput faster, it
only removes the per-call dispatch tax (91% of Python's total here).

Two zero-behavior-change optimizations applied to corr_score_candidate:
  1. exp(-a) * exp(-b) == exp(-(a+b))  (exact identity, not an
     approximation) -- combined angle+distance (or centre+radius)
     Gaussian terms into ONE expf() call instead of two.
  2. Early-exit prefilter: skip a static line entirely once
     angle_diff > 3*SIGMA_ANGLE_RAD (contribution would be < 1.2e-4,
     negligible) BEFORE computing the distance term or calling expf()
     at all. Same idea soft_scan_matcher.py's own docstring flags as
     "the first optimization to reach for" -- it was needed. Same
     prefilter applied to arcs on radius difference. NOTE: currently
     only covers the angle/radius axis, NOT the distance/centre-distance
     axis -- flagged as a follow-up (see NOT DONE below).

Result: pure C algorithm cost dropped 33.0ms -> 26.7ms/call on host
(~19% further win). Confirmed -O3 -march=native gives NO additional
gain -- GCC cannot auto-vectorize a branchy, expf()-heavy loop; this
is a real ceiling for scalar code, not a compiler-flag problem.
Re-verified all 3 test levels still pass after the optimization --
behaviour-preserving, not just faster.

Host summary: Python 98.5ms/call -> C 26.7ms/call ~= 3.7x, marshalling
excluded from both sides.

DECISIONS MADE FROM THIS DATA
--------------------------------
RT Linux -- NOT pursued. Stddev is a clean 2-9% of mean at every map
  size (9.2), max never spikes far above p95. That's ordinary
  measurement noise, not scheduling jitter -- if OS scheduling/
  preemption were the dominant problem, occasional large outliers would
  show up, and they don't. RT Linux (PREEMPT_RT) reduces scheduling
  latency/jitter, it does not make correlative_search() execute one
  FLOP faster -- and the data shows jitter isn't the problem here, mean
  latency is. Not worth the kernel-level effort for this bottleneck.

Lookup table -- justified, agreed as the next concrete step. At
  n_static=60 (realistic, matches real hardware log's S:43-60 range),
  the algorithm alone is 194ms mean -- consistently, reproducibly ~1.9x
  over budget. Low noise means this number can be trusted enough to act
  on. NEON/SIMD vectorization considered and deliberately NOT chosen
  first: expf() isn't NEON-vectorized by GCC's autovectorizer (confirmed,
  -O3 -march=native gave nothing), so a real SIMD win would require
  writing/validating a custom vectorized exp approximation -- high
  complexity, untestable for real performance on the x86 sandbox this
  work was done in (QEMU-NEON is functionally correct but not
  representative of real Cortex-A53 NEON throughput). A scalar lookup
  table is lower-risk, doesn't need NEON to pay off (table lookup+lerp
  is 3-5x cheaper than a full expf() call even scalar, since it skips
  expf()'s own argument-reduction/polynomial evaluation), and is easy
  to validate against the existing 3-level test suite.

the 100ms/10Hz budget at realistic map sizes (194ms vs 100ms at
n_static=60). NOT a complete fix.

NOT DONE / FOLLOW-UP REQUIRED (do not read this commit as "problem solved")
------------------------------------------------------------------------------
1. Lookup table itself -- designed (domain t = na^2+nd^2 or nc^2+nr^2,
   table generated offline in Python at build time as a static const C
   array, linear interpolation, clamp-to-zero beyond ~3 sigma) but NOT
   IMPLEMENTED. Must validate against all 3 test levels after building,
   especially T5 (parallel-wall ambiguity -- score-comparison sensitive
   to quantization error).
2. Distance/centre-distance early-exit prefilter not yet added (only
   angle/radius are currently pruned) -- needed to bound the lookup
   table's domain tightly, and is a free win on its own regardless of
   the table.
3. soft_scan_matcher.py ("fine" stage) is now a comparably-large
   contributor (86-105ms on real hardware, 9.3) and is still pure
   Python -- next porting candidate after the lookup table.
4. map_manager.c still doesn't exist -- CorrMapEntry is a stand-in.
   Fold into real MapEntry/ENTRY_* once map_manager.h is written (pure
   rename, fields were named for this).
5. cpufreq governor/frequency sysfs paths unreadable on this board even
   as root -- unresolved, low priority given 9.2's low-jitter result
   already answered the question that check was meant to inform.
6. pose_estimator.c, line_matcher.c, slam.c itself remain Python-only --
   this commit ports ONE module deeply and validates it thoroughly; the
   same "mirror scalar reference, profile before optimizing, validate
   on real hardware not just host" discipline should apply to each of
   these, not a quick mechanical repeat.
